## Releasing

Releases are published to npm from GitHub Actions with [trusted publishing](https://docs.npmjs.com/trusted-publishers), so no npm token is stored and every version carries a provenance attestation. To release, bump `version` in `package.json` (and its `@rulebookguard/site` and `@rulebookguard/symbols` peer ranges), in `packages/site/package.json`, in `packages/symbols/package.json`, in `plugin/.claude-plugin/plugin.json`, in `plugin/plugin.json`, in `plugin/mcp.json` and in the pinned commands of `README.md` and `README.es.md` (tests keep them equal), merge it to `main`, then push a matching tag:

```sh
git tag v0.1.0
git push origin v0.1.0
```

It publishes `@rulebookguard/site`, then `@rulebookguard/symbols` (whose `prepack` copies the grammar files into it), then `rulebookguard`. Trusted publishing is configured per package on npmjs.com, and a package must exist before it can be configured, so before the first release that includes a new package, publish a placeholder version of it once by hand (for example `npm version 0.0.0-setup.0 --no-git-tag-version` then `npm publish --access public --tag setup` from its directory, without committing the version change) and add its trusted publisher. Never hand-publish the release version itself: the workflow's own `npm publish` of it would then fail after the packages before it are already public.

The `Release` workflow fails without publishing when the tag does not match the package versions, or when `vp check`, `vp test` or `vp pack` fails.

It also publishes an `npm-shrinkwrap.json`, generated by `scripts/write-shrinkwrap.ts` and not committed, that locks the production dependencies to the versions in `pnpm-lock.yaml`, the ones `vp test` ran. This is what makes a pinned `npx rulebookguard@<version>` reproducible for projects with no lockfile entry for it, so to ship a newer dependency, update `pnpm-lock.yaml`. The workflow fails without publishing when a production package is an alias or resolves to two versions in `pnpm-lock.yaml` (`vp test` catches both before a tag), when npm cannot lock exactly those versions, or when the packed CLI cannot lint this repository.

After publishing, `scripts/check-published.ts` confirms what only the real registry can prove: that it reports `_hasShrinkwrap: true`, and that installing the new version yields the locked versions. If this last step fails the version is already public, so inspect it, and deprecate it if needed, rather than re-running the workflow.
